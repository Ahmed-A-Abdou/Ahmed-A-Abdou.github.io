Cam3 Horror Game

The Concept
Cam3 is built around a single deliberate constraint: the only tool that keeps you safe costs something to use. Watching the monster through security cameras keeps it at bay — but every second the camera runs drains your battery. Attention itself becomes a resource.

Beyond the design concept, Cam3 became my primary architecture project — rebuilt from the ground up after a previous version failed because everything depended on everything else. Every system was designed with strict boundaries and minimal coupling.
Architecture — Event-Driven ScriptableObject Layer
Two complementary asset-driven layers carry all cross-system communication:
  • SO_Event / SOEventListener — publisher/subscriber. Publishers hold a SO_Event asset reference and call Raise(); listeners are MonoBehaviours that self-register in OnEnable, unregister in OnDisable, and fire a UnityEvent response wired in the inspector. 11 event assets currently in the project.
  • ScriptableVariable — an abstract base with BoolVariable, FloatVariable, IntVariable, StringVariable, Vector3Variable and GameObjectVariable subclasses. Shared runtime state — is the camera up, is the monster visible, current night minute — lives in assets rather than in any single owner, so producers and consumers never meet.
Typed C# Action events cover the two cases where the payload matters and the inspector cannot carry it: CameraSystem.OnCameraPointSwitched(CameraPoint) and MonsterContext.OnNodeChanged(MonsterNode).
Camera System
Singleton-managed controller (CameraSystem.Instance) over a List<CameraPoint>. Each CameraPoint is fully self-contained — a name, a Camera reference, and an IsActive flag; it knows nothing about the controller or any other system. Switching is overloaded by index and by name. Toggling the monitor writes to an IsCameraEnabled BoolVariable rather than notifying anyone directly.

The singleton is the one deliberate exception to the no-direct-reference rule. There is exactly one monitor in the game, so the instance is genuinely unique rather than incidentally global, and cross-system access to it is read-only — the visibility check reads the current camera point and nothing writes back. Routing a single read through an event asset would add indirection without removing the dependency.
Visibility Detection
Visibility is a declarative authoring model rather than a geometric one. Every MonsterNode carries a WatchedByCamera reference, and the monster is visible when currentNode.WatchedByCamera == CameraSystem.CurrentCameraPoint. There is no frustum projection and no raycasting.

It is purely event-driven — visibility recomputes only on a node change or a camera switch, never per frame — and OnVisibilityChanged fires only on an actual state transition, guarded against redundant raises.

The tradeoff is designer-authored coverage instead of geometric truth. It gives up cases like "the monster is technically half-behind a pillar" in exchange for a system that is deterministic, debuggable, tunable per node, and costs zero CPU between events. In a game where each camera view is a fixed shot, geometric occlusion buys nothing that authored coverage does not already express — the camera cannot move to a position the designer did not anticipate.
Enemy AI — 7-State FSM
State pattern over a shared MonsterContext, driven by MonsterStateMachine. The seven states:
StateRole
IdleStateWaits out MoveTimer — but only while unobserved. Watching freezes the timer.
MovingStateWeighted-random traversal of the node graph, then routes to the correct next state
HallwayEndpointStateVisible-to-player node; countdown to the next move, shockable
AtDoorStateTerminal threat — jumpscare countdown, shockable
StunnedStateFreeze after a shock, then forced retreat
RetreatingStateSends the monster back to the starting node
LuredStateProbabilistic relocation with diminishing returns
Node graph: MonsterNode MonoBehaviours hold ConnectedNodes, a NodeWeight, CanSeePlayer / IsFinalPosition flags, and their watching camera. 16 nodes in the playable scene.

The AI's core tension — camera avoidance. In MovingState.FindNextNode(), any candidate node currently on screen has its weight multiplied by CameraAvoidanceMultiplier (0.5) before the weighted roll. So watching a hallway both freezes the monster's idle timer and pushes it away from where you are looking. That is the mechanic the battery cost is paying for.

Escalation floor. CheckChargeMinuteInterval() — once the night clock passes ForceToOfficeMinuteInterval, the monster is teleported to the final node once and only once, guarded by hasChargedOffice. The night cannot be stalled indefinitely by good camera play.

Lure. Success chance is 1 - (usedLureCount × lureResistance) — each use is weaker than the last, and a failed lure still consumes a use.
Resource Management — Battery
Multi-source drain, all configured in a BatteryData ScriptableObject with zero runtime state:
  • Idle drain — constant baseline
  • Continuous tool drain — camera monitor and flashlight, each its own rate
  • Instant-cost drain — shocking the monster is a flat lump-sum charge, gated so it cannot fire below cost
Probability-based failure: once the battery drops past PowerOutageThreshold, a PowerOutageProbability roll can trigger a one-time blackout event — so the exact moment the lights go is not memorisable across runs. A designer tunes threshold and probability independently, with no code changes.
Secondary Threat — Window Monster
Independent staged escalation. A timer advances the threat through a series of discrete positions; reaching the final stage is an instant loss. Player counterplay is sustained rather than instant: holding the flashlight on it both freezes the advance timer and runs a separate repel timer that pushes it back one stage.

Completely decoupled from the primary AI — neither system references the other, and both raise their own kill events into the same win/loss layer.
Time System
Drives the night as discrete minute intervals rather than a continuous clock: RealSecondsPerMinutePeriod real seconds per in-game minute, publishing to a FloatVariable and raising OnIntervalChanged on each tick. The monster's forced-endgame check hangs off that event. Reaching the ending period raises onNightComplete — the win condition.

Current config: minutes 1 through 10, which is nine intervals of 15 seconds — a 135-second night, with the forced charge at minute 8.
Task System
TaskBase — an abstract MonoBehaviour, chosen over an interface because there is real shared behaviour: duration, countdown, active/failed guards, and success/fail event raising all live in the base. Subclasses implement only ExecuteTaskLogic(). BreakerTask is the greybox implementation.
Win / Loss
GameStateManager collects four SO_Events through listeners — monster kill, window kill, battery depletion, night complete — behind a single isGameOver latch so no two outcomes can both fire. Zero references to any system that feeds it.
Player Controller
Two separate control modes as separate components: PlayerController (new Input System plus CharacterController, OnMove/OnLook message-based input, SetCanMove gating) for the mobile state, and DeskLookController (screen-position-driven panning with a dead zone) for the stationary desk state. TorchController binds a held input action to a BoolVariable, so the flashlight's state is what other systems read — not the light component.
Engineering Approach
SOLID throughout. Static config in XData ScriptableObjects, runtime state in XSystem MonoBehaviours, never mixed. Consistent [SerializeField] private with read-only => property encapsulation. One-shot triggers guarded by explicit has* bools so no event can double-fire. Every system built to be developed, tested, and replaced in isolation.
