ZiRunner

The Goal
ZiRunner started as a deceptively simple brief: a multiplayer endless runner. What it became was a shipped, content-driven security awareness training tool disguised as an arcade game — one that runs head-to-head races between players, teaches real cybersecurity concepts through its core loop rather than through a quiz bolted onto the side, and ships fully bilingual in English and Arabic with proper right-to-left rendering.

The engineering goal was never just "make it work." It was to build systems where data ownership, network authority, and content ownership were decided deliberately on day one — so that adding a player, changing a question, or retuning difficulty never means touching code, and so the multiplayer layer never becomes the thing that breaks under load.
Multiplayer — Outcome-Authoritative Networking on Photon PUN 2
Rather than replicating player transforms every tick, I designed the race around a shared-simulation, master-authoritative-outcome model:
  • The host creates a named room with MaxPlayers driven by a ScriptableObject, not a constant. Joiners authenticate against the room name and enter a waiting state.
  • The master client is the sole authority on when the race starts — it gates the start behind a player-count check and broadcasts a single RPC_StartGame to all clients. No client can start early; no client starts late.
  • Each client owns and simulates its own run — its input, its movement, its collisions, its score. That is data the client legitimately owns.
  • On run completion, each client submits its final score via an RPC targeted specifically at the master client (RpcTarget.MasterClient), not broadcast. The master aggregates results in a dictionary keyed by Photon ActorNumber, waits until every expected score has landed, resolves the winner, and broadcasts the result to all clients.
  • Teardown is explicit and ordered: announce → brief delay for UI/SFX → LeaveRoom → Disconnect, with callbacks handling each stage.
The tradeoff I chose, and why: per-frame transform replication would have meant interpolation, lag compensation, and bandwidth scaling as O(players × tickrate) — for a race where players never physically interact. By networking only the outcome, bandwidth is effectively O(1) per run, there is no reconciliation code to maintain, and race fairness comes from a shared config plus master-authoritative scoring instead of from netcode complexity. Player count is a data value — a single IntSO — so scaling from 2 to N racers is a config change, not a code change.
Architecture — ScriptableObject Event/Data Layer
The entire game is wired through a ScriptableObject framework, maintained as a shared git submodule reused across the studio's projects, which I consumed and extended:
  • EventSO / EventListenerSO — a typed, asset-based pub/sub system with ~16 gameplay events (PlusScore, MinusScore, QuestionRequest, ShieldHit, TimerNearFinished, PauseGameEvent, …). Publishers and subscribers never hold references to each other; they hold references to an asset. Events support deferred (end-of-frame) and immediate raising, with per-event debug toggles and inline documentation fields.
  • VariableSO<T> — typed, observable shared state (IntSO, FloatSO, BoolSO, StringSO, Vector2/3SO, GameObjectSO, enum SOs) with change subscriptions, optional persistence caching, implicit conversion to T, and reset-on-exit semantics. ~15 runtime variables (Score, MovementSpeed, Timer, IsMultiplayer, IsPowerUpActive, RequiredPlayers, …) are the game's single source of truth.
  • A ScriptableObject-driven view state machine — the whole game runs in one scene. Loading, Main Menu, Tutorial, Mode Selection, Room Entry, Gameplay, and Game End are seven GameStateSM assets driven by a single state variable, with enter/exit UnityEvent hooks and an IStateListener interface for code-side listeners. No scene loads, no loading screens between menus, no cross-scene reference problems.
  • Custom editor tooling — property drawers and inspectors for every SO type, plus an Event Manager editor window for auditing which listeners are bound to which events. This was the difference between the SO architecture being a liability and being usable by designers.
The practical result: BarrierScript raises MinusScore and OnCollision and knows nothing about the score system, the camera shake, or the audio manager. The question system pauses gameplay without holding a reference to the player. Systems are genuinely independent and individually testable.
Runner Core — Allocation-Free at Steady State
  • Road segment recycling: track segments are held in a Z-sorted ring. When the player crosses an end trigger, the trailing segment is repositioned to the head at a fixed offset. Nothing is instantiated or destroyed during a run.
  • Entity reuse: collectibles, obstacles, and power-ups recycle by toggling collider and renderer state with timed re-enable, rather than spawn/despawn cycles — the same principle applied at object granularity.
  • Environment variation without cost: roadside props swap meshes from a pool on trigger crossing, so a recycled segment does not visibly read as recycled.
Net effect: no GC allocation spikes as the game accelerates, which matters precisely at the moment the game is hardest and frame consistency matters most.

Difficulty ramps by driving a single shared MovementSpeed float toward a cap over time. Road, roadside content, and collision-response logic all read that one value — so speed, penalties, and recovery stay coherent by construction rather than by manual synchronisation.
Player Controller
CharacterController-based with hand-rolled vertical physics rather than rigidbody gravity: explicit gravity accumulation, jump velocity derived from a designer-set jump height (√(2gh)) rather than a magic impulse number, a fall-speed clamp to prevent tunnelling through colliders at high speed, and lateral movement clamped to road bounds by computing the delta actually applied rather than clamping after the fact. Trigger events are guarded by a cooldown coroutine so a single boundary crossing cannot double-fire. Built on Unity's Input System with keyboard and gamepad (Xbox) support.
Content Pipeline — Designers Ship Changes Without a Build
  • Questions.json in StreamingAssets holds 37 bilingual security-awareness questions with parallel EN/AR answer arrays and 1-based correct-answer indices, normalised to 0-based on load and defensively clamped.
  • config.json exposes run duration and the coins-per-question interval.
  • Both load asynchronously at boot via UnityWebRequest coroutines (StreamingAssets-safe across platforms), with explicit fallback defaults on failure so a missing or malformed config degrades to a playable game instead of a crash, then raise a "loaded" event that gates dependent systems.
  • Question selection uses a non-repeating pool that auto-reshuffles on exhaustion, so a player never sees the same question twice in a run.
This was a deliberate ownership decision: question content and difficulty tuning belong to the client and the designers, not to the codebase. They can be edited post-ship without a programmer or a rebuild.
Localization — English/Arabic with Real RTL
  • Unity Localization plus Addressables for UI string tables.
  • RTL TextMeshPro for correct Arabic glyph shaping, ligature joining, and bidirectional text — the part that separates "we support Arabic" from "Arabic actually reads correctly."
  • A locale manager that swaps TMP font assets across the entire scene at runtime, including inactive objects, and flips RTL flags on locale change, with forced mesh updates so Arabic renders immediately rather than one frame late.
  • Question content localises from JSON; UI chrome localises from string tables; the tutorial re-renders its current slide live when the player switches language mid-tutorial.
Game Feel & Supporting Systems
Coin collection drives progression: every N coins (config-driven) raises a question event that pauses the run, presents a localised question, gives DOTween colour-flash feedback with distinct correct/incorrect SFX, applies the score delta, and resumes — pause and resume both routed through events so any system can opt in.

Also built: a singleton AudioManager with a dictionary-keyed SFX library and separated music/SFX buses with independent volume control; EZ Camera Shake on impact; Epic Toon FX particles; a shield power-up with timed expiry that gates all damage sources through a shared IsPowerUpActive flag; a countdown timer with a configurable warning threshold that fires an event in the final seconds (colour shift plus audio cue); a star-rating results screen; and a localised slide-based tutorial.
Key Engineering Decisions
DecisionAlternativeWhy this one
Network the outcome, not the simulation Per-tick transform replication Players never interact physically. O(1) bandwidth per run, zero interpolation/reconciliation code, no desync class of bugs.
Master client owns start and winner; clients own their own run Fully authoritative server Matches actual trust needs for a training tool. Clean, explicit authority boundary with no server infrastructure cost.
Player count as a ScriptableObject Hardcoded 2-player Variable player counts ship as configuration, not as a code branch.
Single scene plus SO state machine Scene-per-screen No load hitches between menus, no cross-scene reference fragility, one place to reason about game state.
SO events/variables as the wiring layer Direct references or a central GameManager Systems stay decoupled and independently testable; designers rewire behaviour in the Inspector without a programmer.
Recycle segments and entities Instantiate/Destroy No steady-state allocation, so frame times stay flat exactly when the game is fastest.
Content in StreamingAssets JSON Content baked into assets or code Questions and tuning are editable post-ship by non-programmers.
What I Learned
Authority is a design decision, not an implementation detail. The most valuable thing this project taught me was to ask "who owns this data?" before writing a line of network code. Once I could answer that per-field — the client owns its run, the master owns the start signal and the verdict — the netcode almost wrote itself, and an entire category of sync bugs never got the chance to exist. I also learned to design around network constraints rather than fight them: the cheapest sync problem is the one you architect out of existence.

Decoupling has to be tooled to survive. A ScriptableObject event system is elegant on day one and unmaintainable on day thirty unless you can answer "what listens to this?" So I invested in editor tooling and inline documentation fields on the assets themselves. That investment is what kept the architecture usable as the project grew past fifty systems.

Object pooling stopped being a technique and became a default. In a game that continuously accelerates, allocation spikes land precisely where the player is least forgiving. Building the runner around reuse from the start — track segments, collectibles, obstacles, props — meant performance was a property of the design instead of an optimisation pass at the end. I now reach for reuse by default in any performance-sensitive context.

Localization is architecture, not a translation task. Supporting Arabic properly meant runtime font swapping, RTL-aware text shaping, forced mesh rebuilds, and a content format with parallel localised arrays — decisions that had to be made early. Retrofitting any of it would have meant rewriting the UI layer.

Making content someone else's job is a feature. Moving questions and tuning into JSON meant the people who actually own the training content could iterate without me. That is the decision I would defend hardest, and the one I would make first on the next project.
