ThreeJs Physics Lab

The Project
A physics simulation platform built in three.js, running three interactive experiments — a nonlinear pendulum, a projectile with air resistance, and a damped spring-mass oscillator — on one shared, schema-driven framework where experiments are fully interchangeable modules.

Built as a technical assessment for a mid-level 3D developer role explicitly graded on architecture, physics correctness, and AI-assisted development practice; developed collaboratively with Claude Code across a full planning-then-implementation cycle.
Framework Architecture
Designed a runtime-enforced Experiment interface — five lifecycle methods plus a static parameter schema — that the entire framework talks to exclusively: sim loop, UI panel, graph and registry all have zero knowledge of which concrete experiment is active.

Since the project is plain JavaScript with no compiler to enforce an interface, the enforcement is built by hand. A constructor guard using new.target blocks instantiating the abstract base class directly, and a prototype-comparison check fails construction immediately, naming the exact missing method, if a subclass omits any required override.
  • Adding a new experiment costs exactly two new files — one physics module, one experiment class — plus a single registry line. Verified concretely by adding three real experiments and one throwaway proof-of-concept, with zero framework files ever touched.
  • UI is entirely schema-driven: a generic panel reads each experiment's {key, label, min, max, step, default} parameter array and auto-generates sliders, with no per-experiment UI code anywhere in the framework.
Physics Implementation
Implemented all three experiments using semi-implicit (symplectic) Euler integration rather than explicit Euler, specifically because explicit Euler injects energy into oscillators every step — visible as a pendulum or spring swinging progressively higher over time with no damping added, which is physically impossible. Used the real, non-linearised equation of motion throughout (sin(theta) for the pendulum, not the small-angle approximation), so the simulation stays correct at large-amplitude, clearly nonlinear swings rather than only near equilibrium.

The half-period bug. When instrumenting the pendulum's oscillation period and the spring's natural frequency, naively timing between any consecutive zero-crossing produces exactly half the true period — a released pendulum crosses equilibrium twice per full swing, once in each direction, before returning to its starting phase. Fixed by filtering zero-crossings to one fixed direction only, so "time between the two most recently recorded crossings" is a full period by construction, with no ×2 correction anywhere in the code. Verified with a hand-built synthetic trajectory test that would fail if the direction filter were ever removed.

Modelled projectile motion with quadratic (velocity-squared) air resistance — the standard drag model for a macroscopic thrown object — while keeping a separate, deliberately idealised drag-free analytic formula (range = v²·sin(2θ)/g) as a fixed comparison baseline, since the coupled drag equations have no closed-form solution and can only be evaluated by simulating.

Demonstrated and unit-tested a genuine physical contrast between the pendulum and the spring: the spring's frequency is amplitude-independent (isochronism, a consequence of Hooke's law being exactly linear), while the pendulum's real period measurably lengthens at large amplitude — the opposite test assertion for each, on purpose.
Testing & Verification
Every physics module is a pure function — plain numbers in, plain numbers out, zero imports, zero dependency on three.js or a browser — enabling a Vitest suite that runs the full symplectic-Euler correctness and period/frequency-vs-theory checks in milliseconds with no rendering context.

Tests were specifically designed to catch integrator-ordering mistakes rather than just final output. For example: releasing an oscillator from rest and asserting that position does change on the very first step — explicit Euler would leave it exactly unchanged, using the old, zero velocity, while semi-implicit Euler would not.
Rendering & Data Pipeline
Built a fixed-timestep accumulator loop decoupling physics from render rate — real elapsed time is banked and drained in identical fixed-size chunks regardless of frame rate, with a clamp preventing a "spiral of death" if the tab is backgrounded and resumes after a long gap.

Enforced strictly one-directional data flow: each experiment's physics module computes new state, and only then does the experiment class copy those numbers onto three.js mesh transforms. Physics never reads anything back off a mesh.

Built a canvas-based live graph that auto-scales to whatever quantity any experiment hands it and exports the full recorded history as CSV, with zero experiment-specific knowledge anywhere in its drawing code.
AI-Collaborative Development Process
Planned architecture and derived the governing physics equations by hand before writing any code, then implemented file-by-file with Claude Code, reviewing and defending every line rather than accepting output wholesale.

Documented two concrete cases where AI output needed correction on review:
  • A test file that hardcoded the experiment count as a literal number, which would break every time an experiment was added or removed — later codified as a standing project rule to prevent recurrence.
  • An early request for the experiment registry to be a class, corrected after review to a plain frozen array once it was clear nothing about the registry needed instantiation or polymorphism.
